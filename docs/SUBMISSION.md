## Inspiration

Every summariser asks you to paste a document into a box and trust it. For a discharge summary, a contract or a payslip that is a real decision — and most tools do not even tell you that a decision was made. Hybrid inference finally makes the honest version possible: the same feature can run locally for private text and in the cloud for text that is not private. We wanted to build the tool that shows its own work.

## What it does

VaultBrief briefs a document in seconds and shows you the privacy cost of doing so.

1. A **local scan** (regular expressions with Luhn validation — not a model) scores the text 0–100 for identifiers, health, finance, credentials and legal terms.
2. A **router** turns that score plus the document length and the device's model availability into an `InferenceMode`.
3. The brief is generated by **Firebase AI Logic**: Gemini Nano on-device for private text, a cloud-hosted Gemini for long public text. Long private documents are briefed map-reduce style in on-device passes.
4. A **privacy receipt** reports where inference actually happened (from `response.inferenceSource`), how many characters were transmitted, how many stayed local, token counts, and any fallback.

If a document is private, the device has no local model and masking is switched off, VaultBrief **refuses to run**. That is the one thing it will not do: send identified text to the cloud.

## How we used Firebase AI Logic

One `getGenerativeModel()` call site, two very different execution environments:

- `getAI(app, { backend: new GoogleAIBackend(), useLimitedUseAppCheckTokens: true })` — limited-use App Check tokens, because generative models enforce replay protection.
- `getGenerativeModel(ai, { mode, inCloudParams: { model: "gemini-3.5-flash-lite", generationConfig: { responseMimeType: "application/json", responseJsonSchema: BRIEF_SCHEMA } }, onDeviceParams: { createOptions: { expectedInputs: [{ type: "text", languages: ["en"] }], … } } })`
- `model.initializeDeviceModel(progressCallback)` is called inside the button's click handler, because Chrome only downloads or resumes the on-device model with user activation.
- `result.response.inferenceSource` is what the receipt prints, and what the ledger counts. We never assume the mode we asked for is the mode that ran.
- The app maps its own policy to all four modes: `ONLY_ON_DEVICE` for private text (refusing rather than falling back), `PREFER_ON_DEVICE` for short public text, `PREFER_IN_CLOUD` for long public text, and `ONLY_IN_CLOUD` for the masked-copy route.

Other Firebase products: **App Check** (reCAPTCHA Enterprise in production, debug token for review builds), **Remote Config** for the sensitivity threshold and model name, **Firestore + Anonymous Auth** to mirror receipts under the user's own anonymous identity (optional, never blocking).

## How we built it

React + TypeScript + Vite, no backend. The engine is pure TypeScript with a strict boundary: `src/engine/hybrid.ts` is the only module that imports `firebase/ai`; everything else is route-agnostic and unit-tested in Node. An MV3 side panel in `extension/` hands the current tab's text to the app.

Firebase Agent Skills (`firebase-ai-logic-basics`) were used for App Check and provider setup guidance, and Chrome's `summary-of-summaries` demo shaped the map-reduce chunking (`measureInputUsage`-style quota awareness, recursive merging).

## Challenges we ran into

- **Two privacy questions, one engine.** A keyword like "diagnosis" should raise the score but must never be rewritten; a card number must be. Our first redaction pass rewrote the word "patient" in the middle of a medical record. Splitting "signal" rules from "value" rules fixed it, and a test now locks it in.
- **Token accounting for a router.** A short private document needs no redaction (it never leaves), a long private one needs chunking, and a sensitive document without a local model needs a masked copy. Modelling "characters that actually crossed the network" instead of "characters processed" made the receipt meaningful.
- **Honest demo mode.** Reviewers will open the app on hardware without Gemini Nano and possibly without our project. The app detects both and says so: a banner, a `simulated` stamp on every receipt, and a device panel that reports `availability` verbatim.

## Accomplishments we are proud of

- A routing engine where the privacy rule is enforced in exactly one place and cannot be bypassed by a policy setting.
- A receipt that is generated from the SDK's own answer rather than from our intent.
- 92 tests including a jsdom run of the entire screen, plus an SDK contract check that calls `generateContent()` against the real SDK with a fake key and proves the request reaches `firebasevertexai.googleapis.com`, and a static MV3 extension check.

## What we learned

Hybrid inference is not "on-device with a fallback". It is a product decision that has to be made in the open: which text may leave, which model answers, and what the user is told afterwards. The SDK gives you the mechanism; the interface has to give the user the receipt.

## What's next

## Testing instructions for judges

1. Open the live demo in Chrome 139+ desktop (on-device path) or any browser (cloud path).
2. Press **Hospital discharge summary** → the routing console shows a device-only route and the receipt shows 0 characters sent. Without Gemini Nano the app offers the masked-copy route instead; switch **Mask identifiers before cloud** off and press *Brief this document* to see it refuse.
3. Press **Public policy newsletter** → the cloud route; the receipt shows the characters that were sent.
4. On a long private document (the NDA) press **Stop** during the map-reduce run: the brief panel reports which pass it stopped after and no receipt is written.
5. `npm test`, `npm run verify:extension`, `node scripts/verify-sdk-path.mjs`.
